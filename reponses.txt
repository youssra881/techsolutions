TP 10 - BASE DE DONNÉES

Création :
CREATE TABLE utilisateurs (
  id INT AUTO_INCREMENT PRIMARY KEY,
  identifiant VARCHAR(30) NOT NULL UNIQUE,
  mot_de_passe VARCHAR(255) NOT NULL,
  prenom VARCHAR(50) NOT NULL,
  nom VARCHAR(50) NOT NULL,
  service VARCHAR(50) NOT NULL,
  role VARCHAR(10) NOT NULL
);

Requêtes demandées :
1. Toutes les lignes : SELECT * FROM utilisateurs; -> 8 lignes
2. Prénom et nom : SELECT prenom, nom FROM utilisateurs; -> 8 lignes
3. Service Technique : SELECT prenom, nom FROM utilisateurs WHERE service = 'Technique'; -> 3 lignes
4. Triées par nom : SELECT id, prenom, nom FROM utilisateurs ORDER BY nom; -> 8 lignes
5. Compte kbenali : SELECT * FROM utilisateurs WHERE identifiant = 'kbenali'; -> 1 ligne
6. Triées par service puis nom : SELECT prenom, nom, service FROM utilisateurs ORDER BY service, nom; -> 8 lignes
7. Sans administrateurs : SELECT prenom, nom FROM utilisateurs WHERE role != 'admin'; -> 7 lignes
8. Service Commercial trié par prénom : SELECT prenom, nom FROM utilisateurs WHERE service = 'Commercial' ORDER BY prenom; -> 2 lignes

Questions :
1. AUTO_INCREMENT donne automatiquement un numéro unique à chaque nouvelle ligne.
2. Les deux mots de passe peuvent être identiques en clair, mais les empreintes sont différentes à cause du sel aléatoire.
3. Pour Emma Lambert, l'id est donné automatiquement par AUTO_INCREMENT ; MySQL ne reprend pas forcément un id supprimé.
4. DELETE FROM utilisateurs; supprimerait toutes les lignes. On restaure les 8 comptes avec le script de remise à zéro du TP 10.

TP 12 - CONNEXION

Le formulaire envoie l'identifiant et le mot de passe avec POST.
verifier.php cherche le compte avec une requête préparée :
SELECT * FROM utilisateurs WHERE identifiant = ?

La vérification est :
if ($utilisateur && password_verify($motdepasse, $utilisateur["mot_de_passe"])) {

Si les deux conditions sont vraies, l'utilisateur est connecté.
Sinon, le site affiche : Identifiant ou mot de passe incorrect.

Tableau des tests :

Questions :
1. Avec GET, les données apparaissent dans l'adresse. Cela est dangereux pour un mot de passe.
2. Sans name="motdepasse", $_POST ne reçoit pas le mot de passe.
3. mot_de_passe contient une empreinte, pas le mot de passe en clair. On utilise password_verify().
4. JMOREAU peut être accepté si l'interclassement de la colonne se termine par _ci.

L'attaque SQL avec ' OR '1'='1 est bloquée grâce à la requête préparée avec ?.


TP 13 - SESSION ET ADMINISTRATEUR

Une session conserve les informations de la personne connectée :
$_SESSION["id"], prenom, nom, service et role.

espace.php vérifie que $_SESSION["id"] existe.
utilisateurs.php vérifie que l'utilisateur existe et que son role est admin.
deconnexion.php utilise session_destroy().

4. jmoreau / Salarie2026 -> Mon espace, sans bouton de gestion

Questions :
1. Le cookie garde surtout l'identifiant de la session. Il ne garde pas le prénom en clair.
2. exit arrête le programme après la redirection. Sans lui, du contenu protégé pourrait quand même s'afficher.
3. Masquer un lien ne protège pas la page. Il faut refaire la vérification dans le fichier PHP.
4. supprimer.php refait la protection car quelqu'un peut écrire directement son adresse ou envoyer son formulaire.
5. creer.php range une empreinte créée par password_hash(). Il ne range pas le mot de passe en clair. Sinon, password_verify() ne pourrait pas vérifier correctement.
