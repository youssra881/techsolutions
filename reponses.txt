Questions TP 10 :

1. AUTO_INCREMENT attribue automatiquement un numéro unique à chaque nouvelle ligne.
Sans cette option, il faudrait fournir soi-même l'identifiant id, avec le risque d'oublier un numéro ou d'utiliser un numéro déjà pris.

2. Julie Moreau et Karim Benali utilisent le même mot de passe, mais leurs empreintes sont différentes.
C'est normal : password_hash ajoute une donnée aléatoire appelée sel. Deux mots de passe identiques peuvent donc produire deux empreintes différentes.

3. Emma Lambert n'a pas reçu l'identifiant 6 après son départ. On ne peut pas prévoir ce résultat pour un nouvel ajout : il faut vérifier la valeur réelle créée par phpMyAdmin.

4. DELETE FROM utilisateurs; supprimerait toutes les lignes de la table utilisateurs.
Pour réparer les dégâts, il faut exécuter le script de remise à zéro du TP 10 afin de recréer les 8 comptes de départ.

Règles importantes :
- UNIQUE sur identifiant : deux salariés ne peuvent pas avoir le même identifiant.
- NOT NULL : les champs concernés ne peuvent pas rester vide.
- DELETE doit toujours avoir un WHERE pour éviter de supprimer toutes les lignes.

Le formulaire envoie les données en POST à verifier.php.

Questions TP 12 :

1. Avec GET, l'identifiant et le mot de passe apparaissent dans la barre d'adresse.
Ce n'est pas acceptable pour une connexion : ces données peuvent rester dans l'historique et les journaux.

2. Sans name="motdepasse", PHP ne reçoit pas la valeur du champ et affiche une erreur indiquant que la clé motdepasse manque dans $_POST.
Le navigateur n'envoie que les champs qui possèdent un attribut name.

3. Impossible d'utiliser == avec une empreinte : mot_de_passe contient le résultat de password_hash, pas le mot de passe en clair.
Il faut utiliser password_verify($motdepasse, $empreinte).

4. JMOREAU est accepté si le interclassement de la base est insensible à la casse.
La comparaison exacte du mot de passe reste sensible aux majuscules.

Sécurité SQL :
Une requête préparée empêche une attaque comme ' OR '1'='1.
Le texte saisi est envoyé séparément du modèle SQL grâce à ? et execute().
Avec une requête SQL construite par concaténation, le texte de l'attaque pourrait modifier la condition SQL.

Questions TP 13 :

1. Le cookie de localhost contient surtout l'identifiant de la session PHP.
Il ne contient pas directement le prénom. Le prénom est gardé côté serveur dans $_SESSION.

2. Sans exit après header(), le script pourrait continuer à produire du HTML malgré la redirection.
exit arrête immédiatement l'exécution et évite qu'une page protégée soit affichée.

3. Masquer un lien est une règle d'affichage seulement.
La protection doit exister dans utilisateurs.php, supprimer.php, ajouter.php et creer.php.

4. La protection est répétée dans les pages qui agissent, car un utilisateur peut taper directement l'adresse ou envoyer le formulaire sans passer par le bouton.

5. creer.php range une empreinte avec password_hash.
Si le mot de passe était rangé en clair, une fuite de base révélerait tous les mots de passe.
À la connexion, password_verify ne pourrait pas fonctionner correctement avec le mot de passe clair.
